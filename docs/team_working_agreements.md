## 1. เกณฑ์การประเมินขนาดงานด้วย Story Points (Estimation Framework)

ทีมตกลงประเมินขนาดงานด้วย **Story Points** (Relative Sizing) แทนการนับชั่วโมงทำงาน (Man-Hours) เพื่อลดความคลาดเคลื่อนจากทักษะส่วนบุคคล และประเมินจาก 3 ปัจจัยร่วมกัน:
1. **Amount of Effort:** ปริมาณงานที่ต้องลงมือทำ (จำนวน Models, Forms, Views, Templates)
2. **Complexity:** ความซับซ้อนทางเทคนิคและตรรกะ (เช่น การคำนวณต้นทุน, การหักสต็อกอัตโนมัติ)
3. **Risk & Uncertainty:** ความเสี่ยงและความไม่แน่นอนในเครื่องมือหรือโค้ดส่วนที่เชื่อมต่อ

### ชุดตัวเลขมาตรฐาน: Modified Fibonacci Sequence
ทีมใช้ตัวเลข: **1, 2, 3, 5, 8, 13, 20**
* หากงานใดประเมินได้ **13 แต้มขึ้นไป** ถือว่าเป็น Epic ที่ใหญ่เกินไป ต้องทำ **Story Slicing** แตกย่อยเป็น Story เล็กๆ ก่อนดึงเข้า Sprint

---

### เกณฑ์เปรียบเทียบมาตรฐานของทีม (Golden Reference Stories)
เพื่อเป็นบรรทัดฐานเดียวกันในการทำ Planning Poker:

| แต้ม (Points) | ระดับความยาก | นิยามและเกณฑ์เปรียบเทียบ | ตัวอย่างงานในระบบร้านอาหาร |
| :---: | :--- | :--- | :--- |
| **1 แต้ม** | ง่ายมาก (Trivial) | งานเล็ก ไร้ความเสี่ยง ไม่กระทบฐานข้อมูลหรือ Logic อื่น | เพิ่ม Checkbox สถานะ หรือปรับสไตล์ CSS ปุ่มบนหน้าเว็บเดิม |
| **2 แต้ม** | เล็ก (Small) | เพิ่มฟิลด์ใหม่บน Model เดิม พร้อมอัปเดต ModelForm พื้นฐาน | เพิ่มฟิลด์ `unit` ในวัตถุดิบ หรือเพิ่มปุ่มลบพร้อมยืนยัน Modal |
| **3 แต้ม** | ปานกลาง (Standard) | งาน CRUD ทั่วไป 1 โมเดล มี Form + View + Template พื้นฐาน | หน้าแสดงรายการและเพิ่มหมวดหมู่วัตถุดิบ (`IngredientCategory`) |
| **5 แต้ม** | ซับซ้อน (Medium/Complex) | มี Business Logic ข้ามโมเดล มีการตรวจสอบสิทธิ์ หรือความปลอดภัย | ระบบ Auth & CustomUser, ระบบตัดสต็อกอัตโนมัติผ่าน POS |
| **8 แต้ม** | ซับซ้อนสูง (Large) | มีสถาปัตยกรรมระดับระบบ ต้องแบ่งงานย่อย | ระบบสรุปบัญชีและรายงานความเคลื่อนไหวสต็อกย้อนหลังขนาดใหญ่ |

| User Story ID | หัวข้องาน (PBI Title) | ผู้รับผิดชอบหลัก | ความซับซ้อนและเหตุผล | Story Points |

| **US-02** | ระบบคลังวัตถุดิบ & จัดการสต็อกเข้า (Ingredient & Barcode) | คนที่ 2 | โมเดลวัตถุดิบ, ฟอร์มรับของเข้าทั้งแบบกรอกเองและสแกนบาร์โค้ด, Validation และ Tenant Isolation | **5** |
| **US-03** | ระบบจัดการเมนูอาหารและสูตรวัตถุดิบ (Recipe/BOM) | คนที่ 3 | เชื่อมโยง `MenuItem` กับ `RecipeItem`, คำนวณต้นทุนต่อจานไดนามิก, และป้องกันวัตถุดิบข้ามร้าน | **5** |
| **US-04** | ระบบ Mini-POS ตัดสต็อก & เตือนของหมดล็อกการสั่ง | คนที่ 4 | หน้าจอ POS เช็คสต็อกเรียลไทม์ ล็อกปุ่มสั่งเมื่อวัตถุดิบหมด, ตัดสต็อกอัตโนมัติด้วย Atomic `F()` | **5** |
| **US-05** | ระบบแดชบอร์ดสรุปต้นทุน & วิเคราะห์ผสาน AI (AI Analytics) | คนที่ 5 | คำนวณต้นทุนต่อจาน, สรุปยอดขาย และเชื่อมต่อ AI API (Gemini) แนะนำการสั่งซื้อและคุมต้นทุน | **5** |

## 2. ข้อตกลงความพร้อม: Definition of Ready (DoR)

**นิยาม:** เกณฑ์ข้อตกลงร่วมกันของทีมว่า User Story ชิ้นใดมีความชัดเจนและข้อมูลครบถ้วนพอที่จะ **"พร้อมดึงเข้าสู่การวางแผน Sprint 1"** โดยไม่ติดขัดระหว่างเขียนโค้ด

### รายการตรวจสอบ DoR Checklist (ทุก Story ต้องผ่านครบทุกข้อ):
1. **User Story Format:** เขียนตามโครงสร้างมาตรฐานสมบูรณ์  
   `As a <ผู้ใช้งาน>, I want <ความต้องการ>, So that <คุณค่าที่ได้รับ>`
2. **INVEST Criteria:** มีคุณค่าต่อผู้ใช้จริง (Valuable) และมีขนาดเล็กพอที่จะทำเสร็จภายใน 1 Sprint (Small)
3. **Acceptance Criteria (AC):** มีเงื่อนไขการตรวจรับงานอย่างชัดเจนอย่างน้อย 3–5 ข้อ (ระบุทั้งกรณีสำเร็จและกรณีข้อมูลผิดพลาด)
4. **Data & UI Specification:** มีโครงสร้างฟิลด์ของ Data Model และตัวอย่าง Mockup หน้าจอคร่าวๆ
5. **No External Dependency:** ไม่มีงานภายนอกที่ยังคั่งค้าง หรือต้องรองานอื่นที่ยังไม่เริ่ม
6. **Estimation Consensus:** ผ่านการพูดคุยและโหวตแต้ม Story Points ร่วมกันทั้งทีมแล้ว

## 3. ข้อตกลงความเสร็จสมบูรณ์: Definition of Done (DoD)

**นิยาม:** ข้อตกลงร่วมกันของทีมวิศวกรซอฟต์แวร์ว่า ชิ้นงานจะถือว่า **"เสร็จสมบูรณ์ 100% พร้อมส่งมอบและตรวจรับงาน"** ก็ต่อเมื่อผ่านเกณฑ์คุณภาพทางเทคนิคครบทุกข้อ

> *"Done ไม่ได้แปลว่าแค่เขียนโค้ดเสร็จบนเครื่องตนเอง (Never say 'It works on my machine!')"*

### รายการตรวจสอบ DoD Checklist (ก่อนปิด Issue และส่งงาน):
1. **Coding Standard:** โค้ดเขียนตามมาตรฐาน PEP 8 สะอาด จัดย่อหน้าถูกต้อง และมี Docstrings ระบุรหัส Use Case (เช่น `# [UC-02]`) กำกับทุก View
2. **Acceptance Criteria Met:** ผ่านการทดสอบเงื่อนไข Acceptance Criteria ครบทุกข้อตามที่ระบุใน Issue
3. **Security Checked:**
   * ทุกฟอร์มที่มีการส่งข้อมูลแบบ POST ต้องฝังแท็ก `{% csrf_token %}`
   * ทุก View ที่ต้องการความปลอดภัยต้องใส่ `@login_required`
   * มีการทำ Field Validation เพื่อป้องกันข้อมูลผิดพลาดและช่องโหว่ความปลอดภัย
4. **Peer Code Review:** ต้องสร้าง Pull Request (PR) เข้า branch `main` และได้รับการตรวจสอบพร้อมกด **Approve จากเพื่อนร่วมทีมอย่างน้อย 1 คน**
5. **Issue Linked:** มีการระบุคีย์เวิร์ดปิด Issue อัตโนมัติในคำอธิบาย PR เช่น `Closes #1`
6. **Clean Merge:** รวมโค้ดเข้าสู่ branch `main` ได้อย่างสมบูรณ์โดยไม่มี Merge Conflict ค้างอยู่
7. **Deployable / Runnable:** สามารถรันคำสั่ง `python manage.py runserver` บนเครื่องของเพื่อนในทีมแล้วทำงานได้ตามปกติ

## 4. ข้อความเทมเพลตสำหรับโพสต์ลง GitHub Issue

### หัวข้อ Issue:
`[Team Agreement] Definition of Ready (DoR) and Definition of Done (DoD)`

### เนื้อหา Issue (สามารถ Copy ไปวางได้ทันที):
```markdown
## Team Working Agreements (หมูแองกี้เบิ้ด)

### Definition of Ready (DoR)
- [ ] User Story สมบูรณ์ (As a... I want... So that...)
- [ ] มี Acceptance Criteria ชัดเจนอย่างน้อย 3 ข้อ
- [ ] มีโครงสร้างโมเดลและหน้าจอ UI คร่าวๆ
- [ ] ประเมินแต้ม Story Points ด้วย Modified Fibonacci แล้ว (1-8 แต้ม)
- [ ] ไม่มี Dependency ค้าง

### Definition of Done (DoD)
- [ ] โค้ดตรงตาม PEP 8 และมี Docstrings ระบุรหัส [UC-xx]
- [ ] ทำงานผ่าน Acceptance Criteria ครบถ้วน
- [ ] มี {% csrf_token %} และ @login_required ป้องกันความปลอดภัย
- [ ] เปิด Pull Request และผ่าน Peer Code Review ได้รับ Approve อย่างน้อย 1 คน
- [ ] มีคีย์เวิร์ด Closes #... ปิด Issue อัตโนมัติ
- [ ] รวมเข้า main โดยไม่มี Merge Conflict
```
